# 首批示范与第一次训练

> **首批历史安排与实验记录。** 已完成首批的用户请按[当前 12 条清单](next-capture-batch.md)补录，具体操作统一看[真人示范录制操作规范](recording-operation-standard.md)。不要重复执行下方历史采集数量和试训参数；已保存的旧示范、模型继续保留。

目标是先让小视觉策略在 **Lotus 固定短路线** 上学会移动、转向、停稳射击，再让模型自己跑，按实际失败补数据。第一轮不是完整地图、真实客户端、5v5 或技能训练，也不以验证集动作准确率代替游戏成功率。

## 先验收一条记录

1. 关闭旧选关器和旧录制游戏，重新运行项目根目录 `start_windows.cmd`。
2. 选择“路线行走 / 训练示范 / 变化编号 42”。点击“开始本机录制”，在游戏按 Enter。
3. 看旁边路线示意：箭头是自己，蓝线是参考路线，绿色圆是 A 入口训练区终点。正常走、正常转弯即可，不用刻意踩中每个蓝点，不要跑到别的区域等待结束。
4. 游戏出现“任务完成”后按 Enter，回到选关器看见“示范已保存，可上传供云端训练”。未完成、Esc 放弃和质量检查失败的记录不会进入训练。
5. 先确认这条有效，才开始下表。已有失败记录保留用于诊断，不改成成功、不删除质量检测。

## 第一批采多少

以下是启动小样本实验的工作量建议，不是达到真人能力所需的数据量保证。先录完两个课程就训练和评估，不等待所有课程录完。

| 课程 | 训练示范 | 独立验证 | 怎么操作 |
| --- | --- | --- | --- |
| 路线行走 | 42–49，共 8 条 | 142–144，共 3 条 | 顺畅走到绿色终点，少停留、不乱跳、不空枪 |
| 停稳射击 | 50–61，共 12 条 | 150–152，共 3 条 | 沿路接敌，松开移动键、瞄准、短点射，击倒后继续到终点 |

第一条验收成功的 42 计入这批。总共 **20 条训练 + 6 条独立验证**。每次手动填写下一个变化编号；它只改变本关初始条件，不更换路线。课程完成后选择会保留。数据按整段示范划分，不能把一条录像的相邻帧拆成训练和验证两份。轻微自然纠正可以保留；迷路、长时间发呆、持续撞墙或卡顿的失败段不当作正面参考。

目前起点变化只有约 0.2 米、朝向约 ±12°（调整视角课更大），敌人位置基本固定。验证编号独立仍然是很窄的分布，不能把它称为跨地图泛化。后续拓展路线时，需要同时设计任务/目的地输入，不能让纯画面策略面对同一画面却被要求去不同终点。

## 录完后怎么交接

真人只需在选关器点击“上传成功示范”。它把 `runs/demonstrations-v215` 的有效游戏帧、动作、元数据作为 GitHub Release 附件上传；仓库公开，附件也公开。该按钮不推送代码，不会自动启动云端训练。全部输入均来自游戏窗口，不录桌面、麦克风或其他应用。

云端必须先使用相同的 v2.15.0 引擎、Lotus 资源、动作合同及本次新终点规则。拉取 `windows-recorder` 的当前修复并重新运行准备/构建流程后，再导入示范。数据 Release 的标签指向打包当时已有的提交，不代表当前训练代码版本；不要检出该数据标签作为训练环境。本地改好或推送代码不等于服务器已更新，不要用旧服务器引擎训练或评估这些新示范。

同版本 Linux 环境就绪后，按顺序执行（先进入虚拟环境和项目目录）：

```bash
python -m valorant_lab.exchange pull --kind demos \
  --directory runs/demonstrations-v215
valorant-lab bc-train --data runs/demonstrations-v215 \
  --scenario configs/lotus_movement_combat.json \
  --device cuda --epochs 10 --output runs/bc-round01
bash scripts/run_cloud.sh evaluate --model runs/bc-round01/best.zip \
  --scenario configs/lotus_route.json --split dev --episodes 20 \
  --queue runs/corrections-v215 --output runs/bc-round01-eval-route
bash scripts/run_cloud.sh evaluate --model runs/bc-round01/best.zip \
  --scenario configs/lotus_shooting.json --split dev --episodes 20 \
  --queue runs/corrections-v215 --output runs/bc-round01-eval-shooting
```

BC 离线训练不需要开游戏进程；闭环评估需要云端渲染，但不需要桌面图标。记录训练/验证样本数、损失、每个动作头的统计，同时查看路线成功率、击倒后是否继续行走、超时、撞墙、抬头/低头、乱开枪等失败。用新的输出目录保留每轮模型和数据批次，不覆盖上一轮。

当前人机协作方式为 **Windows 本机录制/纠正 → GitHub Release 交换数据 → Linux 云端训练与自动评估**。云端无需常开远程桌面、VNC 或浏览器串流供真人操作。这里的云端“渲染”只指模型自动跑游戏时生成第一人称画面；没有人在远程观看，视觉模型仍然需要这些画面。离线 BC 只读取已录制数据，可与游戏评估分阶段运行；后续在线强化学习采样才需要游戏环境与模型交互。

### GPU 数据准备与吞吐

`bc-train` 默认使用 `--data-cache auto --cache-mib 1024`：校验示范后，在总计 1 GiB 的缓存预算内一次解压训练和验证画面。模型在 CUDA 上且显存余量足够时，原始 uint8 图像、动作和历史索引直接缓存到显存；逐批在 GPU 上组装 4 帧历史。缓存不足以放入显存时使用 CPU 内存，超过总预算则保留有界流式读取，并在启动日志说明原因。自动选择最多使用当时空闲显存的四分之一作为缓存，并保留至少 2 GiB 余量；批次本身仍需额外显存。

首批 2742 帧的原始 RGB 约 289 MiB，无需重复存储四份历史。缓存仍按整段示范处理边界，首帧补零；训练和验证保持分开。数据合同、动作、随机抽样顺序和默认 batch=32 不变，不会为了占满显存自动增大批次或模型。

启动日志及 `runtime.json` 记录实际计算设备、缓存位置、解压耗时和预算；`metrics.json` 每轮记录训练样本/秒、训练与验证耗时及 CUDA 峰值分配/保留显存。计算耗时不包含保存检查点；整轮总耗时还需考虑数据首次加载和模型保存。显存使用量不等于 GPU 忙碌比例，应结合吞吐和最终游戏评估判断。

可明确选择 `--data-cache cpu`、`--data-cache cuda` 或用 `--data-cache stream` 复现旧读取路径。显式缓存模式预算不足会报错，不静默超额分配。复现实机对比可运行：

```bash
python scripts/benchmark_bc.py --data runs/demonstrations-v215 \
  --device cuda --modes stream auto --batch-size 32 --batches 8
```

该命令对真实数据做少量临时训练计算并保存性能报告，不保存模型、不替换正式训练结果。先在相同批次/学习率/种子下验证缓存提速；增大批次会改变每轮更新次数，应另做训练效果对比。

较大 batch 的测速可增加 `--full-batches`，跨多次打乱后的数据遍历采满指定数量的完整批次，排除最后不足一批对比较的影响；它要求 batch 不大于训练样本数。该开关只影响测速，正常训练仍保留最后不足一批的样本。

`batch-size` 是每次梯度更新处理的样本数，增大会增加中间激活所需显存；`epochs` 是完整遍历训练集的次数，主要增加训练时间，不会按轮数累积显存。首批只有 2117 个训练样本：batch32 每轮 67 次更新，batch256 为 9 次，batch512 为 5 次。因此不能只增大 batch 又保持原来 10 轮，否则更新次数会大幅减少。比较参数时同时记录更新次数、验证损失和游戏表现，保留验证损失最好的 `best.zip`，不要直接用最后一轮代替最好的一轮。

### 当前 16GB V100 的大批次参数

对首批数据已实际完成 batch512×140轮、batch2048×350轮的比较，两者均为 700 次梯度更新。后者的完整批次短时吞吐约 1.13 万帧/秒，PyTorch 峰值预留约 11.3GiB；本次验证损失较低，但仍需游戏闭环评估。当前可使用下面的大批次试训设置，保持学习率不变：

```bash
valorant-lab bc-train --data runs/demonstrations-v215 \
  --scenario configs/lotus_movement_combat.json \
  --device cuda --data-cache cuda --cache-mib 1024 \
  --batch-size 2048 --epochs 350 --learning-rate 0.0003 \
  --checkpoint-every-epochs 10 --cpu-threads 4 --seed 42 \
  --output runs/bc-v100-large-01
```

此命令需要包含缓存和存档间隔修复的代码版本，每次试验使用新输出目录。`--checkpoint-every-epochs 10` 每轮仍做验证，立即把当时最好的完整模型与优化器序列化到 CPU 内存，在首轮、第 10/20/... 轮和最后一轮将最新模型及尚未写盘的最佳模型落盘。这样最后一轮退步也不会丢掉较早的最佳权重；异常终止时，最近一个落盘点之后的改进可能尚未保存。未指定该参数时仍默认每轮落盘。

350 轮是当前数据的有限试验预算，不是所有后续数据集的固定训练长度；此次最好的验证结果出现在第 294 轮。数据量、GPU 空闲显存或模型结构变化后重新测速。batch2117 已经覆盖整个训练集，本次比 2048 的吞吐提升不足 0.1%，无需再扩大到超过真实样本数。约 11.7GiB 是本次训练的实测整卡峰值，不是人为设定的显存上限，剩余空间也没有划给远程试玩。离线 BC 不需为游戏渲染预留固定份额；缓存预算之外仍要容纳模型、梯度、优化器状态和 CUDA 临时工作区，按实测峰值保留适当波动余量即可。

### 混合精度与独立游戏进程

含性能修复的版本支持在上述 BC 命令增加 `--precision amp-fp16`。本次 V100 完整 350 轮对照从 86.94 秒降到 56.10 秒，具体效果和验证边界见[验证记录](validation.md#2026-11-27混合精度与多进程自动评估)。它仅适用于 CUDA：卷积和演员网络采用 FP16 自动混合精度，输入从 uint8 直接转换并归一化；动作概率、损失、验证和导出的参数仍用 FP32。训练使用梯度缩放，在裁剪梯度前先还原缩放，并记录实际更新次数与因非有限梯度跳过的更新；损失出现 NaN/Inf 时停止，不覆盖以前的检查点。默认仍为 `fp32`，Windows 录制/加载模型不需要开启 AMP。

自动游戏评估支持 `--workers N`。每个进程拥有独立游戏、种子片段和日志；完成后由主进程校验、汇总，并串行写入纠错队列，避免多个游戏同时修改同一道纠错题。只用于 lockstep 批量评估；`--realtime` 与单道 `--case` 保持 `--workers 1`。并行通过率不能冒充单机实时流畅度。

实机 10 个可用 CPU 核的当前选择：BC 使用 `--cpu-threads 4`；评估使用 `--workers 8 --cpu-threads 8 --device cpu`。8 个相同场景的实测中，四路为 87.40 秒，八路为 51.30 秒，轨迹一致。后一个线程参数是所有推理进程共享的预算，每进程至少一线程。每帧的小模型推理在 CPU，游戏画面由 NVIDIA 渲染。不会因为 `--device cpu` 将游戏改成软件渲染。不要使用宿主机显示的 96 核来创建 96 个训练/游戏进程；以容器 CPU affinity 和 cgroup 配额为准。其他机器从 1/2/4 路开始测速，不能直接套用八路。

```bash
export OMP_NUM_THREADS=1
export MKL_NUM_THREADS=1
export OPENBLAS_NUM_THREADS=1
bash scripts/run_cloud.sh evaluate --model runs/bc-v100-large-01/best.zip \
  --scenario configs/lotus_route.json --split dev --episodes 20 \
  --workers 8 --cpu-threads 8 --device cpu \
  --queue runs/corrections-v215 --output runs/bc-fast-eval-route-01
```

并行模式必须使用新的输出目录。详细轨迹与截图在 `workers/worker-*/episode-*`，总报告的 `artifact_directory` 指向对应证据；有工作进程失败时不发布完整成功报告。先做 BC，再启动游戏评估，两个阶段分别使用 GPU，不需要常开远程真人串流。

矩池云当前持久卷是约 5GB 的 FUSE 挂载，实例盘约 200GB。频繁的小文件、逐步轨迹可先写实例盘；完整模型、指标和纠错题及时复制到持久卷并校验哈希，确认保存后再关闭实例。直接把训练检查点写到持久卷最省管理；本次对照实验在实例盘计时，每个训练完成后另存并校验持久副本，复制时间不计入训练速度。不要把内存盘或实例盘当作永久数据盘。

## 第一轮之后

1. **先看模型自己玩。** 训练损失下降仅说明更像演示动作；模型走偏后的画面分布不同，必须通过闭环实测发现问题。成功率先作为基线，20 次只是小样本检查。
2. **按失败补录。** 优先处理最常见的撞墙、方向错误、未停稳射击。确有需要时再追加“换弹与前进”6+2、“调整视角”6+2、“组合交战”10+3 条训练/验证。这些数量同样是预算建议，后续按效果调整。
3. **保留旧示范一起学习。** 新纠错与旧正常动作混合，避免只学某一种困境。当前 `bc-train` 每次重新初始化模型，尚不支持从上轮 BC 权重续训；第二轮若要继承权重，应先实现并验证 BC 续训和数据混采，不能把重复运行命令说成已经增量训练。PPO 已有独立的初始化/恢复接口。
4. **再做奖励微调。** 能稳定移动和射击后，从 BC 初始化 PPO，逐项检查奖励是否鼓励刷分、空枪或停滞。更多路线/出生点/敌人位置、独立测试集、阶段训练与防遗忘检查在扩大任务时补上。
5. **最后升级人机纠错。** 现在题包是从原种子重做完整回合，不是失败瞬间接管；需要世界状态快照、连续观测历史和严格的动作时序对齐，才能实现真正的失败状态接管。无需让人整天看训练，只在待纠错题形成后集中处理。

## 分享对话核对与补充

已读取用户提供的[《腾讯开悟训练方式》对话](https://chatgpt.com/share/6b091080-f5bc-83e9-ac4e-fa1bea34e9f6)。其中“BC 起步 → 人工纠错 → 强化学习 → 自动评估再纠错”的总体思路适合本项目，但需要明确实现边界：

- 环境交互、有奖惩目标的是强化学习，不因没有逐帧人工标签就叫无监督学习。开悟是训练平台，课程学习、模仿学习、强化学习分别是不同层面的训练方法。
- 当前只有真人从起点完整重做的纠错流程，不能直接称作已经实现 DAgger/HG-DAgger。DAgger 的关键是针对当前策略访问到的状态取得专家动作并聚合训练，动机是减轻模仿学习的分布偏移和误差累积。参见 [Ross 等人的原始论文](https://proceedings.mlr.press/v15/ross11a.html)。
- 分享对话强调继承原模型和混合旧数据，这一点应保留；代码现状是 PPO 可恢复，而 BC 尚需补续训。人工操作必须和当时看到的画面对应，不能把晚几秒的纠正动作贴到早先帧上。
- 人看路线提示属于教师辅助信息。模型只吃原始游戏 RGB；旁路引导不能进训练图像。后续如果更换目标地点，必须让模型得到玩家可获得的任务目标，不能只在奖励器里偷偷换终点。
- CS:GO 的像素行为克隆已有公开研究和代码，支持从视觉示范起步这个方向，但其数据规模、任务和游戏不同，不能据此承诺几十条演示就能流畅打全局。参见[论文](https://arxiv.org/abs/2104.04258)与[微软公开代码](https://github.com/microsoft/imitation_learning_in_modern_video_games)。
- 当前执行策略是小型 CNN、4 帧历史和离散动作头，以 20 Hz 决策、60 Hz 物理步进运行，没有每一步调用大语言模型。部署量化可以稍后做，现阶段仍应保留实际推理耗时与连续运行速度的验收；20 Hz 是设计频率，不是任何 CPU 上已验证的性能。

先跑通一条有效真人示范，再做第一轮小批量 BC。没有接受的数据时，不用合成测试轨迹冒充真人示范，也不宣称模型已经训练完成。
## 当前实验入口：先修复学习质量

2026-11-27 的旧模型诊断显示，吞吐优化后的模型仍可能几乎只输出向前走，
不转向、不射击。因此下文的大 batch/GPU 性能记录保留作历史对照，不能当作
模型已经学会游戏的证明，也不应直接无限增加 epoch。

新的有限实验入口见 [自动训练与评估](automatic-experiments.md)。它固定比较最多
三组归一化/动作权重方案，使用 batch 128，自动生成训练检查点、画面依赖诊断、
实际游戏射击/命中/任务成功率和失败轨迹。默认 CLI 仍保留 legacy 架构兼容旧模型；
新候选由 manifest 显式指定，尚未自动替换旧模型或正式部署。
