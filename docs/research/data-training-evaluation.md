# 数据、训练与评估规范

更新：2026-11-25。本文保留完整规范与候选实验设计；0.2 版已实现分块示范、BC/PPO、开发纠错队列和分组评估，具体字段及命令见[使用手册](../stage1-guide.md)。下面概念字段不等于当前解析器的字段名。返回[研究目录](README.md)。

## 1. 三种材料不要混为一谈

| 材料 | 用途 | 不能直接推断的东西 |
|---|---|---|
| 教程、论坛、评论 | 发现任务、坏习惯、失败情境和教学顺序 | 不直接提供同步键鼠动作标签 |
| 操作示范 | 学习画面到动作的关系与时序 | 不保证所有示范都合理或覆盖模型犯错状态 |
| 独立评估回合 | 判断学会什么、哪里失败、是否连续 | 不能同时用于调参和宣称最终泛化 |

相关机制见[参考项目](reference-projects.md)：CS:GO BC 的数据链路、DAgger 的状态分布问题、机器人工作的同步示范和动作序列。以下规范是本项目设计，未经完整实验验证。

## 2. 先锁定一份场景清单

每个实验至少记录：地图资源哈希与区域、出生范围、目标类型/尺寸/行为、武器配置、伤害规则、护甲、画面与 HUD 设置、动作映射、时间单位、成功/失败/截断条件、奖励版本、随机种子。

正式示范采集前，按[路线图的参数核验要求](project-status-and-roadmap.md)记录移动、停止、视角、射击精度、弹药和换弹基线，先修复影响任务成立的机制错误。后续物理参数变更应建立新版本，并明确旧示范与模型是否仍兼容；不能把不同机制的数据无标识混合。

初期可以统一发放固定枪械，以便单独学习控制；这不代表普通经济回合能永远购买该枪。自动补弹、无限弹药、目标高亮、辅助路标等教学便利都应记入清单，最终评估不能悄悄保留。

现有约 4 米的标记导航是环境自检配置。1A 正式训练和验收另建无辅助路标的场景，目的地来自事先公开的固定任务；若开展带辅助标记的诊断实验，数据和成绩单独标注。基础血量、弹药等从可见 HUD 获取，不能用诊断真值补进策略输入。

## 3. 示范记录格式

建议用“回合元数据 + 图像/视频 + 动作序列 + 训练诊断”分层保存。下面是概念字段，不是当前解析器已支持的协议。

```json
{
  "schema_version": "proposed-demo-v1",
  "episode_id": "lotus-route-a-0001",
  "scenario_id": "proposed-lotus-route-a",
  "source": "human",
  "observation": {
    "frame_id": 120,
    "capture_time_ns": 4000000000,
    "image_ref": "frames/000120.png"
  },
  "action": {
    "based_on_frame_id": 120,
    "request_time_ns": 4008000000,
    "applied_time_ns": 4012000000,
    "duration_ms": 50,
    "forward": 1,
    "strafe": 0,
    "yaw_delta_deg": 0.4,
    "pitch_delta_deg": 0.0,
    "fire_held": false,
    "reload_request": false
  },
  "task_context": "follow_fixed_route"
}
```

数值仅示意。生产数据要保存未量化鼠标输入、执行后的实际转角、保持状态与释放边缘、丢弃/超时原因、结束类型，以及完整配置引用。不要靠压缩视频帧号假定固定时长；记录真实时间戳和帧间隔。

真值、奖励事件、可见性标注单独存放，不出现在 actor 输入。事件带唯一 ID，伤害、击杀、安装等只能结算一次。首批采用单进程单调时钟；若以后跨进程/设备，应记录时钟映射和误差。

## 4. 示范来源与质量

### 人工示范

先少量录制：无敌人走图、固定目标、移动后射击、换弹、走偏恢复。检查按键时序和画面后再扩大。成功示范和恢复示范都需要；不因某段最终击杀就忽略前面的乱扫、看地或多余换弹。

### 脚本示范

适用于明确、可重复的短任务与正确性基线。公开的路线目标可以事先配置；目标接敌与开火标签必须以允许的可见信息为依据。不能因为场景知道敌人的出生坐标，就在看不到时提前瞄准并将其混为普通视觉示范。

若为调试使用了额外状态，标明教师依赖，单独存放。检查相同玩家观察是否会因隐藏状态不同得到相互矛盾的动作；这样的样本不能直接要求纯视觉学生确定性模仿。

### 质量闸门

- 用回放核对请求动作与实际动作；异常延迟、丢帧、错误回合拼接需显式标记。
- 检查任务是否真正完成，结束动作是否释放，回合重置后记忆是否清空。
- 保留无目标、遮挡、低弹药、队友挡视线等情况；评估集保留真实频率，不能只测试成功样本。
- 人类、脚本、模型自采、纠错样本分别标注来源；不同策略版本保留标识。
- 数据量先服务于可解释失败，再扩充；不从论文或教学视频照搬固定小时数。

## 5. 训练顺序与基线

| 实验 | 目的 | 需要比较的结果 |
|---|---|---|
| B0 脚本/人工控制 | 验证场景、动作和奖励实现正确 | 目标是否可达、命中与完成是否正确结算 |
| B1 现有 PPO 帧堆叠 | 保留最简单训练对照 | 学习速度、任务完成与典型失败 |
| B2 小型视觉记忆策略 + BC | 从示范建立动作与序列基础 | 单项成绩及脱离示范后的闭环偏差 |
| B3 BC + 纠错数据 | 补充自主运行产生的恢复状态 | 走偏、卡墙、跟丢和任务恢复是否改善 |
| B4 在可靠基线上 PPO 微调 | 优化任务结果与新情境适应 | 是否提升目标指标且不破坏已有技能 |

B1—B4 用相同留出任务和预算口径比较。BC 的损失下降不能代替实际游戏成功。循环网络按序列训练，保留初始记忆和回合边界；padding、burn-in 等训练细节在实现时固定并记录。

纠错循环：模型独立运行 → 按失败类别采样 → 人工或经审核的教师提供后续动作 → 合并有来源标记的数据 → 重训 → 用未用于纠错的评估集比较。若改了动作/观察契约，先完成数据迁移或重录，不直接混用。

PPO 微调保留旧模型回滚点和旧任务回归集。必要时保留示范监督或与参考策略的约束；这是候选稳定措施，不是已验证的默认损失配方。

## 6. 课程组合

第一组：转向、移动、停止与短路线。第二组：可见目标定位、停稳射击、开火结束、换弹。第三组：移动交战切换及失败恢复。第四组：跟随、守点、目标交互和基础回合。

每组先固定部分条件，再逐项增加难度。变动因素包括出生朝向、目标位置、距离、遮挡、弹量、对手动作和画面变化。新增能力后保留旧课程样本或回归检查，防止遗忘。

具体场景采用[20 张训练卡](training-task-cards.md)。卡片的所有指标与阈值仍需在实际环境中定标。

## 7. 奖励设计与常见投机

可以使用如下分解描述后续多任务奖励。0.2 版移动交战已设置一组初始权重，见[环境说明](../environment.md)，尚未通过学习曲线证明最优：

`任务完成事件 + 有效交战事件 + 有限的任务进展 − 无效操作/停滞/时间代价`

这只是结构说明。导航进展应考虑可达路线或阶段目标；单看穿墙直线距离可能鼓励顶墙。等待守点有时是正确动作，不能一律按“不移动”惩罚。换弹和后撤需结合当前任务解释。

| 设计问题 | 可能学出的错误 | 验证与修正 |
|---|---|---|
| 按移动距离加分 | 绕圈、跑离目标 | 记录阶段完成与重复路径 |
| 按开火/换弹动作加分 | 空扫、反复换弹 | 只认有效事件，加入空场景 |
| 按靠近队友加分 | 贴人、堵退路 | 同时检查阻挡、视线和任务进展 |
| 死亡惩罚过大 | 永远躲出生点 | 对比不参与策略的回报 |
| 只奖击杀 | 守包时追人，忘记交互 | 单独评估目标职责 |
| 每步相同惩罚但改变决策频率 | 仅频率改变就改变最优行为 | 按模拟秒归一化时间代价与折扣时间尺度 |
| 重复计算事件 | 通过重置/反复触发刷分 | 事件 ID 去重，明确回合生命周期 |

奖励函数输出和策略观察是两条通路；可以用真值计算奖励，但不能把奖励所依赖的隐藏位置作为运行输入。

## 8. 数据切分和评估矩阵

按回合、轨迹来源、场景种子切分，不把相邻帧随机分入训练和测试。纠错时使用开发集；最终测试集锁定，避免反复针对同一失败样本调参。

| 层级 | 变化范围 | 能回答的问题 |
|---|---|---|
| 固定场景检查 | 相同配置，明确动作输入 | 环境和奖励是否正确 |
| 同分布留出 | 未见过的回合/种子 | 是否学到该课程 |
| 同图扰动 | 新起点、朝向、目标位置或遮挡 | 是否只背按键序列 |
| 组合任务 | 导航、交战、恢复和交互相接 | 是否能保持职责 |
| 跨设置/地图 | 画面、物理或地图变化 | 能力迁移边界在哪里 |
| 目标硬件实时运行 | 游戏和模型同机 | 实际闭环是否连续 |

每项报告成功数/总数、耗时分布、失败原因。初始 100 回合和 90%/80% 门槛见[路线图](project-status-and-roadmap.md)，仅在写明条件时有意义；长期比较增加训练种子，并报告不确定性。

## 9. 连续性和延迟

至少记录：画面形成、捕获结束、预处理结束、推理开始/结束、动作入队、动作应用时刻。计算新观察年龄、推理延迟、端到端延迟和错过决策周期的比例。

预热后以 batch=1 在游戏和模型同负载下运行，初始可采用连续 10 分钟观察；报告 p50/p95/p99、最长停顿、CPU/GPU 占用、显存、游戏帧时间。训练 samples/s、模型推理 FPS、游戏显示 FPS 和新决策 Hz 分别列出。

原速录像应包含失败和恢复，不用倍速、插帧或挑选单次成功片段代替验证。准星抖动、频繁反向转动、无理由停枪和连续空放都应作为可审查事件。

## 10. 服务器运行与可复现产物

当前可用的 record、replay、bc-train、train、evaluate 和 queue 命令见[使用手册](../stage1-guide.md)。除 smoke 外默认使用移动交战任务。人工数据用于 BC，不能直接塞入 PPO rollout。真人数据与模型达标结果仍待后续采集训练。

后续每次实验保存：代码 SHA、依赖清单、驱动/硬件与实际渲染设备、地图哈希、完整场景配置、观察/动作/奖励版本、数据清单、随机种子、训练步数、最佳与最后权重、评估结果、原速录像。

先 1 个环境检查稳定性，再测 2/4/8 等并发的吞吐和资源占用。PyTorch 能使用 CUDA 不等于 Godot 正在硬件渲染；Xvfb 也不等于 GPU 加速。确认瓶颈后再增加环境或调整图像传输。

代码、配置和文档随 Git；大规模录像、数据集、训练日志和权重单独管理，用清单、哈希和访问方式关联，不提交到普通源码历史。当前已审核的地图包按既有[资源说明](../assets.md)管理。

## 11. 一次实验报告应能回答什么

1. 相比哪个基线，只改变了什么？
2. 模型运行时实际收到哪些信息？
3. 哪些任务变好，哪些变差；成功分母是多少？
4. 是否存在信息泄漏、奖励投机或数据切分污染？
5. 原速回放和整条延迟链路是否支持“连续运行”的结论？
6. 新机器能否用同一配置恢复并复现评估？

只有这些问题能回答，才决定扩大训练、增加地图或进入部署优化。
